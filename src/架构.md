# 当前架构总结

> 本文记录当前代码的实际组织方式，并与 `docs/最终架构规范.md` 的目标边界区分。它不是发行说明，也不替代规范文档。

## 1. 总体调用链

规范定义的主链为：

```text
API → Workflow / Service → DatabaseService → Repository / QueryRepository → ORM
```

当前实现总体沿用该方向：API 路由负责协议、鉴权和参数；Workflow/Tasks 编排业务；Services 提供业务与基础设施入口；`DatabaseService` 管理事务并暴露 Repository 代理；Repository 操作 ORM。`service_container` 在启动时注册并提供 DatabaseService、TaskManager、ScraperManager 等全局服务。

但这只是当前主要结构，不代表全 `src/` 已经严格满足规范。仓库仍有历史兼容入口和边界未完全收敛，文档不应把“目标架构”写成“全量已达标”。

## 2. 数据库、配置、缓存与文件

- 数据库访问的正式入口是 `get_database_service()`；调用方在 `db.transaction()` 中声明事务，DatabaseService 管理 session、提交/回滚和 Repository/QueryRepository 生命周期。
- Repository 负责单表 CRUD 或复杂查询，写操作原则上只 `flush()`，提交由上层事务负责；DatabaseService 是 Repository 的统一收口。
- 配置由 `ConfigService` 访问，配置值采用内存缓存并回退数据库；启动阶段会预加载部分代理和 scraper 配置。
- 缓存由 `CacheService` 统一访问。其 hybrid 模式以内存为 L1、数据库为 L2，读取 miss 回填 L1，写入先更新 L1 并异步落 L2，重启后可由持久层回填。
- 文件系统操作统一由 `FileStorageService` 提供基础读写、复制、清理和文件探测能力；资源下载、备份恢复、版本整合、部署校验与更新决策属于资源编排层。
- 规范要求配置、缓存、文件分别走服务入口；实际代码已形成这些服务，但仍可见历史模块直接组合基础能力，不能宣称所有路径均已完全迁移。

## 3. Scraper 与 API 2 公共依赖

`scrapers/base.py` 是来源公共依赖门面和 `BaseScraper` 基类：公共 DTO、协议依赖和纯工具函数从此处显式选择导入。各平台 scraper（`src/scrapers/`）依赖 `.base` 聚合。

API 2 的公共依赖聚合是导入与契约边界，公共依赖导入不共享实例状态。来源构造接收配置服务和 TransportManager，管理器在启动组装时注入其他协作者。

ScraperManager 负责发现、初始化、配置缓存和来源生命周期。来源外部网络适配不应反向调用 Tasks、通知或 Repository；数据库访问仍应通过服务层完成。

## 4. TaskManager 与下载专用管理器

`src/services/task_manager.py` 的通用 `TaskManager` 面向导入、刷新、搜索、管理、后备等后台任务：维护多个队列和 worker，支持暂停、恢复、取消、通知、恢复依赖和任务处理器注册。规范要求业务任务通过 `TaskManager.submit_task()` 提交，并由 Service/Workflow 执行。

`src/services/download_task_manager.py` 是另一条下载资源管理路径，不能与通用 TaskManager 混称。它只管理 scraper 资源包下载任务的状态、进度、取消、当前任务和有限历史，使用英文 `pending/running/completed/failed/cancelled` 状态，并携带 `need_restart`、`restart_pending` 等资源部署字段。它与 SSE 连接解耦，下载可在后台继续，前端通过状态流查询。

## 5. Scraper 资源下载与部署

资源接口位于 `src/api/ui/scraper_resources.py`，只负责 HTTP 参数、鉴权、错误映射与响应构造，复杂调用统一进入 `src/workflows/scraper_resources/workflow.py`。后台下载真实实现位于同目录的 `executor.py`，自动更新由 `auto_update.py` 编排，内部轮询入口只负责调度。

`resources.py` 承担资源包获取、解压校验、备份恢复与部署流程；版本清单整合和更新判定也归该编排目录。编排调用现有 ConfigService、CacheService、FileStorageService、ScraperManager 和 DownloadTaskManager，不把复合业务包装成新的服务。纯版本格式判断留在工具层，文件及网络基础能力通过下层服务使用。

现有机制包括：

- 后台任务状态写入 `DownloadTaskManager`，并可写入 CacheService 供查询/重连使用；
- SSE 进度端点按任务状态推送，完成路径发送 `done`；
- 需要替换运行中的源文件时使用 `restart_pending`，先让 SSE 发送终态，再执行延迟覆盖或容器重启；
- 版本查询使用共享 `resource_version_cache`，下载后清理以重新读取文件；
- 下载锁、版本缓存及缓存区域常量由资源编排的 `state.py` 统一定义；所有入口共享同一状态对象，不保留旧目录转发实现。

## 6. 启动组合与前端关系

启动入口是 `src.main`。它创建 FastAPI、注册 API、MCP、PWA 和静态资源路由，生命周期委托 `src.core.app_lifecycle.run_startup/run_shutdown`。

启动组合大致为：预加载配置 → 创建 session factory 与 DatabaseService → 初始化 ConfigService、CacheService、TransportManager → 创建 MetadataService、ScraperManager 并初始化来源 → 创建 TaskManager 及任务处理器 → 注册媒体、Webhook、性能等服务 → 启动 worker 和恢复流程。组合根负责依赖注入，避免 Service 反向导入 Tasks。

前端不是独立后端层：生产构建产物由 `src/frontend.py` 挂载，API 由 FastAPI 路由提供；资源下载页面使用 scraper 资源 API 与 SSE 进度端点，后台任务状态和缓存使页面断开后仍可查询任务结果。开发环境则重定向到前端开发服务器。

## 7. 文件夹职责列表（按架构层）

### 7.1 数据库交互层

- `src/db/orm_models.py`：SQLAlchemy ORM 模型、表关系、索引和持久化对象定义。
- `src/db/repositories/`：Repository 与 QueryRepository；负责单表 CRUD、跨表查询、聚合和搜索，只操作 ORM 与当前 Session。
- `src/services/database_service.py`：数据库访问唯一服务入口，管理 session、事务提交/回滚，并向上层暴露 Repository 代理。
- `src/services/service_container.py`：注册和获取全局 DatabaseService；上层通过 `get_database_service()` 进入数据库链路。

调用方向是：`API / Workflow / Task / Job → DatabaseService → Repository / QueryRepository → ORM`。规范要求上层不直接实例化 Repository 或操作 ORM；当前仓库仍存在历史兼容边界，不能据此宣称全 `src/` 已完全清理。

### 7.2 服务层

- `src/services/`：业务服务和基础设施服务的集中目录，包含数据库、配置、缓存、文件、任务、来源、媒体、通知等服务。
- `src/services/config_service.py`：配置读写、默认值注册、内存缓存和失效管理；配置缺失时回退数据库。
- `src/services/cache_service.py`：统一缓存入口；支持内存、Redis、数据库及 hybrid L1/L2 协调和回填。
- `src/services/file_storage_service.py`：通用文件系统能力入口，收口文件读写及相关存储操作。
- `src/services/task_manager.py`：通用后台任务队列、worker、暂停/恢复/取消、通知和任务处理器管理。
- `src/services/download_task_manager.py`：scraper 资源包专用下载任务状态、进度、取消、当前任务和历史管理。

### 7.3 工具层

- `src/utils/`：通用工具目录，目标是提供无状态、低耦合的解析、诊断、运行时和基础辅助函数。
- `src/utils/parsing/`：标题、文件名、协议、弹幕等解析工具。
- `src/utils/runtime/`：传输、容器、服务器实例和运行时适配工具。
- `src/utils/diagnostics/`：任务上下文、异常、性能跟踪等诊断辅助。
- `src/utils/parsing/versions.py`：无 I/O 的版本格式判断；资源下载与版本文件操作不放在工具层。

### 7.4 编排层

- `src/workflows/`：跨服务业务流程编排，覆盖搜索、匹配、导入、刷新、下载、弹幕和日历等流程。
- `src/workflows/scraper_resources/`：手动下载、旧版流式下载、自动更新、版本清单、备份恢复和部署的统一资源编排。
- `src/tasks/`：后台任务实现；通过通用 TaskManager 提交并调用 Workflow/Service 执行业务。
- `src/jobs/`：定时任务和调度适配，触发刷新、同步、维护等后台流程。
- `src/internal_tasks/`：应用内部维护任务，例如 scraper 资源更新等，不是 HTTP API 层。
- `src/scrapers/`：各平台来源实现及 `base.py` 公共契约；属于外部数据源适配边界，由 ScraperManager 在启动时组装。

### 7.5 API 层

- `src/api/`：FastAPI 路由总目录，负责 HTTP 协议、鉴权、参数校验、响应序列化和 SSE 传输。
- `src/api/control/`：控制类 API，例如导入、搜索、配置和资源管理。
- `src/api/ui/`：面向 Web UI 的 API；scraper 资源下载 API 在 `src/api/ui/scraper_resources.py`。
- `src/api/dandan/`：DanDanPlay 兼容 API。
- `src/api/dependencies.py` 等依赖模块：提供请求级鉴权和服务依赖注入，不承担跨域业务编排。

### 7.6 支撑目录

- `src/schemas/`：Pydantic 请求/响应模型、DTO、枚举和协议数据结构。
- `src/core/`：应用配置、生命周期、缓存驱动和启动基础设施；`app_lifecycle.py` 是主要组合根。
- `src/frontend.py` 与 `web/`：前端构建产物、PWA 路由和静态资源挂载；前端通过 API/SSE 与后端交互。
- `src/routes/`、`src/webhook/`、`src/commands/`：补充路由、Webhook 入口和命令入口，最终调用服务或编排层。

## 8. 现有遗留边界与阅读口径

- 规范禁止 API/Workflow/Tasks 直接操作 Repository/ORM，但当前仓库仍存在历史兼容代码和复杂流程，不能假称全 `src/` 无违规。
- 资源下载本次已统一归编排层；仍需在后续修改中维持 API → Workflow → 基础服务的依赖方向，不能重新把复合流程放回工具层或新增资源业务 Service。
- Service Container 的部分服务采用惰性或显式注册，启动顺序和依赖注入仍是组合根职责；不要把全局单例描述为任意位置可自由实例化。
- 本文记录当前代码的主要结构与规范关系，不将其他模块未核实的理想状态描述为已经达标。
